# V for Victory to World at War: D-Day

Game installations, generated scenario packs and extracted artwork are local
data, excluded from Git. See the [repository setup guide](../README.md#run-the-editor)
and [scenario pack index](SCENARIO_PACK.md) to prepare them.

> Use the complete `INVADE-PATCHED.EXE` for exported scenarios. It includes the
> **version 4** engine fixes described below.
> The original weather-only extension left a separate
> 260-entry victory-history buffer unchanged; v4 expands that to 400 too,
> preventing late-turn memory corruption. Native and older patched saves load;
> v4 saves require v4 because they contain the extended victory block. See
> [patch notes](../game/waw/patches/README.md).

Updated 2026-10-06 from `disasm/disasm_v4v.txt`, the staged files in `game/v4v`, the native D-Day
scenarios, and the protected-mode code/debug symbols in
`game/waw/dday/INVADE.EXE`.

The converter supports the **27 staged V for Victory 2.1 scenarios**. Its output
is an **experimental D-Day adaptation**, not a lossless port of the V4V engine.
The generated files are structurally checked and usable in the editor. The
400-entry weather patch removes the original fixed-date and 260-entry limits.
It does not reproduce V4V combat, AI or supply rules. The newer
[game-profiles layer](GAME_PROFILES.md) adds adapted V4V winter arithmetic
and pre-scenario ground accumulation to new editor/CLI imports. See the
[patch and DOSBox-X test notes](../game/waw/patches/README.md) for actual runtime coverage
and remaining failures; structural validation alone does not establish playability.

All **27 scenarios are already exported** with current profiles and matching
artwork in `scenarios/dos/SCENARIO`, alongside the
16 earlier WaW scenarios. Copy the pack's `V4V` subfolder into the patched D-Day
installation's `SCENARIO` folder and
[SELECT.BAT](../game/waw/dday/SELECT.BAT) from `game/waw/dday` into the game directory.
Run `SELECT` to stage a battle. No individual conversion/export is needed.
See the [pack index and installation steps](SCENARIO_PACK.md).

## Convert, edit, and test

```sh
python3 scenario_converter.py game/v4v --dry-run
python3 scenario_converter.py game/v4v -d scenarios/converted/v4v
python3 scenario_converter.py game/v4v/MGFIRST.SCN -o converted/MGFIRST.SCN
python3 scenario_editor.py scenarios/converted/v4v/MGFIRST.SCN
python3 scenario_converter.py game/v4v --dos -d /tmp/v4v-dos/SCENARIO
```

Python needs the editor's dependencies, including Pillow and Tkinter. The
source `.BTL` and `.RES` files must remain beside each source `.SCN` while
converting. Converted documents carry their artwork and do not need the V4V
installation when subsequently opened or saved.

Each conversion produces:

- `NAME.SCN`: editable D-Day scenario.
- `assets/NAME.SCN.terrain.json`: required terrain artwork and the scenario title.
- `assets/NAME.SCN.counters.json`: required original unit sheets in D-Day bitmap format.

Save and Save As preserve the document and artwork in the `assets` subfolder.
Keep that subfolder when moving scenarios. The SCN format stores references to
artwork, not the pixels themselves. Old JSON artwork files directly beside an
SCN remain supported. Saving creates neither `.bak` files nor a game-tree copy;
temporary rollback files are removed when saving completes.
The converter refuses existing output documents and never modifies its sources.
Detailed reports are optional: add `--report /tmp/v4v-report.json` to write one
diagnostic report with source/output hashes, template choices, terrain mappings,
adjustments and limitations. No reports or summary JSON files are generated by
default. Old reports, backups and the legacy archive have been removed from
`scenarios/converted/v4v`; it contains the 27 D-Day SCNs and their `assets` folder.
The originals under `game/v4v` use the V4V format and cannot replace these conversions.

For subsequent edits, use **File → Export for DOS** to create matching `NAME.SCN`, `NAME.REZ` and
`NAME.AI` files. With the library executable installed, copy all three unchanged
into the playing copy's `SCENARIO` directory. The existing scenario panel lists
them and chooses their graphics/orders automatically. Export generates map
previews, mini-maps and title banners. No launcher or editor JSON is needed on
the playing PC. See the [installation guide](../game/waw/README.md).

Keep the editing SCN and its `assets` folder for further changes. Keep exported
REZ/AI companions in SCENARIO when resuming library saves; their basename is
stored in the save. Older saves without this identity need their original manual
asset setup. The temporary `play` directory was removed.

## Translation coverage and limits

| Data | Conversion |
| --- | --- |
| Briefings | All eight interleaved lines for each side, retaining source bytes |
| Map | Active scenario rectangle cropped from the battleset map; terrain codes translated through the BTL table |
| Roads, railways, rivers, streams, slopes | High 24 bits retained as provisional D-Day directional masks, except river/slope bits on water tiles are cleared; cross-engine gameplay equivalence requires in-game verification |
| Geometry | Odd northern origins expand north by one row to retain hex staggering; out-of-range southern/eastern bounds are clamped |
| Place names | In-bounds labels become D-Day's 32-byte label records, with the count at Scenario+0x122a |
| Artwork | Original large/dim terrain and ground-unit chits; small/night terrain derived from large/dim images |
| Units | All 7,766 records across the 27 scenarios, including inactive and future units |
| Unit fields | Names, side/nationality, class/descriptor, counter number, positions, arrival time, combat ratings, quality/disruption/fatigue, stacking size |
| HQs/support | Rebuilt D-Day auxiliary tables, HQ links and support category lists; ships/aircraft stay off map |
| Objectives | In-bounds positions, names, per-side values and flags; out-of-bounds objectives listed in report |
| Calendar | Source start/end times, date and duration; standalone D-Day campaign start equals scenario start |
| Supply | Source daily quantities and in-bounds entry hexes from the first stock pair; D-Day initial stock/depot defaults; missing in-bounds entries fall back to an on-map HQ/unit |
| Weapon/HQ details | Native D-Day template records chosen by side, class, descriptor, name and mobility; choices listed per unit |
| Victory scoring | D-Day's executable uses score ratios of 2.0 and 1.25 for victory tiers; these are not Bradley SCN thresholds. Objective weights and the template's casualty weights determine points. The Victory block is accumulated scores/history. |
| Weather | Historical source temperatures and weather codes installed with explicit dates in a 1,222-byte weather block; requires the patched D-Day engine. New editor/CLI imports compute initial ground using the adapted V4V game profile; older converted documents retain their previous initial values |
| AI/garrison/replacements | Scripted state, saved orders, garrisons, leaders and replacement schedules reset; HQ staff assistance starts disabled |
| Cosmetic terrain edges/hilltops | Not translated; directional slope masks are retained |
| Ownership/ZOC | Source territorial owner retained; stacking rebuilt from in-play ground units. D-Day recalculates influence at initialization |

After conversion, Scenario Settings can author D-Day leaders, replacement pools
and daily arrivals, HQ garrisons, stock groups, depots, start dates and initial
snow/ice/wetness. These controls do not imply a newly verified translation of
the corresponding V4V systems. Replacement tables now contain nine bytes per
scenario day; saving/exporting older conversions fills missing days with zeros
instead of leaving the engine to read past the previous two-day table.

Native D-Day scenario-specific variant flags and reinforcement randomization
are disabled to avoid applying hardcoded Normandy unit numbers to a foreign
OOB. V4V supply and point values may have different practical effects under
D-Day rules. More detailed field translation and game testing are needed before
calling these faithful or fully playable ports. Winter Velikiye Luki scenarios
still need playtesting of the adapted winter model and remaining rules differences.

### Findings from the new V4V disassembly

The files currently on disk are `disasm/disasm_v4v.txt` and **`disasm/disasm_war.txt`**
(the latter was described in conversation as `disasm_waw.txt`). The WaW listing
is still the DOS loader, not the protected-mode game. The V4V listing includes
resident code, data and overlay stubs; the actual overlay bodies are recoverable
from `game/v4v/V4V.EXE` without another disassembly export.

`tools/v4v_disassemble.py` reads its Borland FBOV header and segment table,
recovers **112 overlays**, resolves relocated far calls through their exported
thunks, and decodes the observed Borland software-x87 instruction forms. It is
a linear research listing, not a complete control-flow analysis: embedded jump
tables may still appear as instructions. It never patches the executable.

```sh
python3 tools/v4v_disassemble.py --segment 24d1 --segment 253d
python3 tools/inspect_v4v_weather.py
python3 tools/inspect_v4v_weather.py game/v4v/VLLAST.SCN --json
```

The disassembler requires `capstone`; the weather inspector uses the editor's
normal dependencies. Segment addresses below use the V4V listing's `0x1000`
load base. Block offsets are payload-relative.

| V4V evidence | Meaning |
| --- | --- |
| FBOV header at file `0x22f20`; bodies based at `0x22f30`; 170-entry segment table at file `0x13dc0` | Overlay selectors index eight-byte segment descriptors; 112 are overlay stubs |
| Overlay `2354:0481`–`0492` | SCN block 7 loaded into the Weather pointer, DS:`06e0` |
| `24d1:03ab` (file `0x6442b`), calling `253d:0000` | Weather creation; Scenario `+0x59 == 0` chooses historical weather, otherwise generated weather |
| Weather `+0xb8`, `+0x414` | Historical weather bytes and signed int16 Fahrenheit temperatures, each with capacity 400 |
| Weather `+0x248`, `+0x734` | Live weather/temperature arrays, initially zero in all 27 staged SCNs; filled by weather creation |
| Weather `+0xb9c`, `+0xba0`, `+0xba4` | Float snow, ice and wetness seeds |
| BTL `+0x16`, `+0x1a` | Battleset start/end timestamps; live weather indexing subtracts BTL start |
| `24d1:04de`–`0543` | Advance the ground-condition seeds through weather before scenario start |
| `253d:0370` (file `0x768f0`) | Snow, ice and wetness update, including freezing at 32 F and a Velikiye-specific ice rule |

All 27 staged scenarios select historical weather. `VictoryScenario.historical_weather`
extracts the authored interval using the BTL origin, rather than reading the
empty live arrays. The shared import layer now advances the ground seeds using
the adapted game profile; the reader itself does not simulate startup or port
the weather generator. Velikiye's valid authored temperatures include negatives;
`VLLAST` starts at table index 332 and ends at 395. Its unused slots 396–399
contain non-weather bytes, so checking all 400 slots as active data is wrong.
The Market Garden campaign's final authored temperature is zero; the inspector
reports it unchanged. The source creation loop copies `BTL end - BTL start`
entries, so end-turn execution order still needs verification before claiming
byte-for-byte equivalence to a running game.

The float seeds are **not** ground conditions at scenario start. For example,
Velikiye stores snow 6.5, ice 4.0 and wetness 0.0, then V4V advances them from
battleset start. Copying those three values directly, or treating their bits as
D-Day integers, would be another incorrect conversion.

D-Day evidence comes from `game/waw/dday/INVADE.EXE`'s named protected-mode
functions, not `disasm/disasm_war.txt`. Code object 1 begins at file `0x53654`:

| Original D-Day function / code offset | Verified behavior before patching |
| --- | --- |
| `RWWeather`, `0x27e1a` | Allocates and reads exactly `0x31a` (794) bytes |
| `SwapWeather`, `0x27dac` | Three int32 ground fields, then 260 int16 temperatures at `+0xc`; 260 weather bytes follow at `+0x214`, with two final state bytes |
| `SetCalUTs`, `0x2f834` | Selects literal weather start/end timestamps using Scenario `+0x1220`, not Calendar's imported dates. Case 0 uses `0x17c70`–`0x17c81` |
| `InitGameData`, call at `0x2fc05` | Calls `SetCalUTs` after loading scenario/calendar data, including saved-game initialization |
| `UpdateWeather`, `0x43b80` | Indexes the weather arrays using Calendar `+0xc` minus the hardcoded weather start |
| `CreateWeather`, `0x43d45` | Option 2 invokes `CreateRealisticWeather`; other values keep the stored sequence |
| `CalcSnowIceWetness`, `0x43a12` | Uses integer arithmetic with different accumulation/melting rules from V4V; does not reproduce V4V's ice growth routine |

For the full Velikiye campaign, timestamps 93950–94342 occupy **393 inclusive
positions**, exceeding 260. Its shorter scenarios fit after rebasing their
weather intervals, even when their source table indexes exceed 260. The patch expands storage to 400 entries and stores explicit start/end dates.
It also expands native 794-byte weather blocks in memory and writes the extended
format to saves. All converted scenarios now include their source historical
weather; no campaign has been shortened. The original staged executable is
unchanged; the patched executable is
`game/waw/dday/INVADE-PATCHED.EXE`.

This separates two reasons for the experimental label: historical weather was
previously **undecoded**, whereas the fixed date origins, smaller storage and
different winter arithmetic are now **verified engine differences**. Supply,
AI, scoring equivalence and weapon-table translation still need further work.

Visual inspection found source edge/feature masks drawing lines across open
sea when interpreted directly by D-Day. The adaptation clears river/slope bits
on water tiles and records the affected hex count. This prevents those sea
overlays; it does not establish the original meaning of V4V's water-edge bits.

### DOS startup corrections

Testing the converted VLCAMP in DOSBox-X found and corrected three additional
loader/initialization errors. These are applied to all 27 refreshed documents:

- `RWHexEdges` (`0x28591`) rejects a zero-length table. Imports now keep one
  unreferenced eight-byte edge record while every hex uses the no-edge sentinel.
- HQ records use unit `+0x80` for parent, `+0x81` for own/assigned HQ, and auxiliary
  `+0x32` for parent index. Root IDs must match so `TraceOneHQ` skips parent `-1`.
  Auxiliary `+0x38` is the cached active flag used by `TraceAllHQs`; it is computed
  from arrival/current time, not inherited from a template.
- D-Day stocks contain **26** X coordinates at `+0x04`, 26 Ys at `+0x38`, an int16
  count at `+0x6c` and 26 unavailable flags at `+0x6e`. The previous converter's
  25-slot/`+0x68` count assumption was wrong (`SwapStock`, `TraceToSupplySource`).

The subsequent **Last odds error** (actually `Latt odds error` in the executable)
was traced to `attack_odds_into_hex` (`0x802e`): it rejects a target owned by the
attacking side. Clearing the source control map falsely assigned every hex to
side 0. It also erased stacking, preventing `InitUnitMap` (`0x31420`) from finding
any starting units. `InitHexZOCs` does not repair either field.

Version 4 preserves bit 16 of each cropped source control cell and rebuilds bits
17–20 from in-play ground units (arrival != -1 and arrival < current timestamp).
Active stacks set their own side; unoccupied hexes retain source territorial
control. The fields are confirmed in V4V `17a1:01c1`/`17a1:01ed` and D-Day
`InitUnitMap`/`hex_ownership` (`0x7801d`). V4V's stacking-size routine at
`1845:0432` returns one for unit `+0x5e == 1`, otherwise three. These values now
populate D-Day unit `+0x7e`; 255 is reserved for HQs, whose size D-Day handles
separately. The converter previously wrote 255 to every unit.

UBCARTER has a 16-point initial stack at source (67, 89), overflowing the four-bit
saved field. The conversion records 15 for that hex to keep it visible at load;
all six units and their individual sizes remain intact. This adjustment is listed
in its report. Tests check ownership, occupancy and sizes across all 27 scenarios
and reject the previous empty/wrong-side control maps.

The odds check remains enabled in the executable. Existing saves made from the
broken conversion retain its bad state; start a new game from the refreshed SCN.
See the patch notes for actual DOSBox-X test coverage and remaining rule differences.

## Verified file structures

Offsets below are **relative to block payloads**, unless explicitly marked
as file offsets. All sizes/indexes are little-endian.

A V4V SCN is 26 or 27 consecutive blocks, each introduced by a uint32 byte
length. The first `0x00000c0c` is the Scenario block's **length**, not an
independent magic followed by a short header. All 27 files parse to exact EOF.

| Block | Layout |
| --- | --- |
| 0 | Scenario, 3,084 bytes |
| 1 | Calendar, 44 bytes |
| 2 | Whole-battleset hex map: row-major uint16 indexes |
| 3 | Shared hex records: 4 bytes each |
| 4 | ZOC/ownership, 4 bytes per map cell |
| 5 / 6 | Side 0 / side 1 OOB, 156 bytes per unit |
| 7 | Weather/configuration, 2,986 bytes |
| 8 | Daily supply, four bytes per scenario day |
| 9 | Stock structures, 236 or 472 bytes |
| Optional 10 | Garrison data in the 27-block layouts |
| 12th from end | Objective records, 42 bytes each |
| Final five | Five 160-byte state blocks |

The remaining blocks are preserved in the source files, not assumed to be
D-Day-compatible. The converter creates a complete native D-Day block sequence
using `UnitRoster`; it does not concatenate the old blocks behind a new header.

### Scenario and battleset

- Scenario `+1`: battleset ID, 0–3; `+2`: scenario index within that battleset.
  These are not version and difficulty.
- Scenario `+4`: float 2.1 in the staged files, not 2.05.
- Scenario `+8`: four int16 values: top, left, bottom, right.
- Scenario `+0x16` / `+0x1a`: int32 scenario start/end timestamps.
- Scenario `+0x7e`: eight interleaved pairs of 128-byte briefing lines.
- Scenario `+0x87e`: int16 label count; `+0x880`: 30-byte label records
  (X, Y, font byte, 25-byte name).
  The destination has 50 slots at `+0xbe0`, with count at `+0x122a`.
  The earlier converter incorrectly wrote that count to `+0x1221` (difficulty)
  while retaining the template's label count. This is fixed for new conversions;
  existing converted SCNs are not automatically rewritten. Reconvert the source
  or edit its place-name list in Map → Tools to correct an older document.
- Each BTL contains one length-prefixed 1,774-byte payload. Full-map inclusive
  Rect is at `+6`; its right/bottom determine width/height, not the subscenario
  rectangle in the SCN.
- BTL `+0x1e`: 16-byte local-to-master terrain table; `+0x2e`: theater title;
  `+0x42f`: 25-byte scenario-title slots.

V4V master terrain IDs are translated to D-Day as follows:

| V4V master | D-Day | Name |
| ---: | ---: | --- |
| 0–6 | 0–6 | Bocage, clear, forest, swamp, town, water, beach |
| 7 | 9 | Fortress |
| 8 | 10 | City |
| 9 | 13 | Invasion beach |
| 10 | 7 | Bunker |
| 11 | 8 | Beach bunker |
| 12 | 12 | Airfield |
| 13 | 11 | Rubble |
| 14 | 14 | Special/blank graphics; not ordinary terrain |

### OOB record

| V4V offset | Meaning / D-Day destination |
| --- | --- |
| `+0`, `+2` | int16 OB ID and counter number -> `+0x54`, `+0x56` |
| `+4`, `+6` | int16 X/Y -> relocated `+0x58`, `+0x5a` |
| `+0x10` | int32 arrival -> `+8`; -1 remains inactive |
| `+0x18`–`+0x1d` | Side, nationality, class, descriptor, orders, mobility -> `+0x74`–`+0x79` |
| `+0x24`, `+0x28` | Float base attack/defense -> fixed-point int32 `+0x14`, `+0x18` |
| `+0x2c`, `+0x30` | Float adjusted attack/defense -> `+0x20`, `+0x24` |
| `+0x36`, `+0x3a` | Unaligned float armor/AT -> base/current D-Day ratings |
| `+0x4f`–`+0x53` | Quality, attack/defense quality, disruption, fatigue -> `+0x89`–`+0x8d` |
| `+0x60`, `+0x61` | HQ parent/assignment IDs; source IDs remapped to native zero-based HQ indexes |
| `+0x6a` | Name buffer; every staged name fits D-Day's 26-byte field |

D-Day combat ratings use units of 1,000. Matching Utah units provide evidence
for these field correspondences. Unverified native record fields still come
from templates; this is not a complete specification of either OOB structure.

### V4V resources

RES files begin with a uint16 directory count, followed by 10-byte entries:
reversed four-character type, uint16 ID, uint32 payload offset. Consecutive
resource offsets determine payload lengths.

PICT bitmaps have a 66-byte header, stride at `+4`, inclusive Rect at `+6`, and
bit depth at `+16`. Terrain is 8-bit VGA-indexed data. Unit sheets are packed
4-bit data with the **low nibble first**. Their 18-byte `clut 300/301` resources
contain a uint16 count followed by 16 VGA palette indexes. Unit tiles are
22 × 23 pixels, in 22 columns. One GJS sheet has an extra unused 485th column.
The converter uses D-Day's VGA palette; palette equivalence has been visually
checked, not proven for every source color.

## Validation

`tools/test_v4v_conversion.py` checks all 27 staged scenarios: complete native
serialization, original unit counts/names/ratings/dates, both full briefings,
map-neighbor geometry, HQ chains, auxiliary indexes, support tables, orders
storage, objective bounds, source preservation, collision rejection, dry runs,
and editor Save As retaining the original counters for preparation in the shared game.
`tools/test_v4v_weather.py` checks all authored weather intervals, late-winter
indexing, unused table tails, invalid dates/codes, overlay call resolution and
software floating-point instruction boundaries. Machine-code tests in `tools/test_dday_patch.py` additionally execute the patched
x86 weather routines, including indexes 260 and 392. Actual DOSBox-X results are
recorded separately in the patch notes.

```sh
xvfb-run -a python3 -m unittest discover -s tools -p 'test_*.py' -q
```

The optional `--report` output describes the actual conversions. Structural
checks are separate from DOS runtime testing.
